# ТЗ: модуль тренировок — бизнес-логика

Версия: **0.4**  
Статус: согласовано  
Цель: зафиксировать бизнес-логику для переписывания модуля тренировок на Symfony.

Документ описывает **что** делает система для пользователей, без UI-контрактов, схемы БД и деталей фреймворка.

Схема БД: [tz-trainings-schema.md](./tz-trainings-schema.md).

---

## 1. Цель и границы

### 1.1. Цель

Переписать модуль тренировок City Football с сохранением (и упрощением) бизнес-логики текущего Yii-приложения `training`.

### 1.2. Продуктовый контур v1

В v1 поддерживается **только классический контур фиксированной группы**:

1. Игрок покупает абонемент на **конкретную группу** (или его добавляют в состав).
2. Попадает в **состав группы**.
3. На занятия группы **не записывается** — ходит по расписанию группы.
4. Тренер открывает тренировку, видит состав, отмечает был / не был.

Обязательство игрока = **членство в группе**, не RSVP на конкретную дату.

### 1.3. В scope

- Программы, группы, расписание, конкретные тренировки
- Состав группы (активен / пауза / ушёл)
- Посещаемость
- Абонементы и списание занятий
- Доигровки (current и miss) — разовый приход не из «своего» слота, без отдельного контура front-записи
- Сборы (`TrainingSession`) — в том же рерайте; детализация отдельным подразделом позже
- Email-уведомления по событиям модуля
- Создание/продление абонемента по confirm платёжного шлюза

### 1.4. Вне scope (пока)

- **Front-запись** на тренировку (`TrainingRecord`, `registration_type = frontend`, `use_for_front`)
- **MIX / свободное посещение** (продукт `TYPE_FREE`, списание при брони, квоты отмен 24ч)
- Academia и политики по `source`
- Заморозки (сезонные и по абонементу), summer off-season по freeze
- Пробные тренировки, лид-формы, CRM-воронка
- Каналы уведомлений кроме email (Telegram и др.)
- Полный биллинг/касса: модуль не проводит оплату, только реагирует на confirm шлюза

### 1.5. Биллинг (граница)

Модуль **не** списывает деньги.  
Сценарий: платёжный шлюз подтверждает оплату → система создаёт или продлевает абонемент по купленному продукту и при необходимости включает игрока в состав группы.

## 2. Глоссарий бизнес-терминов

Термины ниже — канонические для v1. Синонимы из legacy / UI приведены в скобках. Если в переписке или коде встречается другое слово — ориентироваться на это определение.

### 2.1. Организационная структура

#### Программа
Линейка тренировочного продукта City Football (например Start, Team, Skills).  
Группирует группы по смыслу предложения клиенту. Не является расписанием и не списывает занятия. У программы есть название, описание, признак публикации.

#### Центр (кампус)
Географическая / организационная площадка верхнего уровня (локация клуба), к которой привязаны поля и группы.  
Пример: конкретный район или база. Не путать с **площадкой** (конкретное поле/зал).

#### Площадка
Конкретное место проведения занятия (поле, зал) внутри центра.  
Указывается в слоте расписания и в экземпляре тренировки. Одна группа может быть связана с несколькими площадками.

#### Сезон
Календарный период учёта (учебный / спортивный сезон), к которому при создании может привязываться тренировка.  
В v1 не используется для заморозок (заморозки вне scope). Нужен для отчётности и привязки занятий к периоду.

---

### 2.2. Группа и люди

#### Группа (тренировочная группа, фиксированная группа)
Постоянный набор игроков с общим расписанием, лимитом мест, тренерами и площадками, в рамках одной программы и центра.  

В v1 группа **всегда фиксированная**:
- игрок входит в **состав**;
- ходит на занятия **этой** группы по её расписанию;
- **не** выбирает каждое занятие через запись с витрины.

Лимит группы = вместимость состава (сколько игроков может одновременно числиться активными).

#### Состав (членство в группе)
Связь «игрок ↔ группа» с жизненным циклом статуса.  
Именно состав, а не запись на дату, определяет, что игрок «относится» к группе и по умолчанию должен быть в списке на её тренировках.

Статусы состава:
- **Активен** — ходит / числится в группе, занимает место в лимите, попадает в список на тренировку.
- **Пауза** — временно не ходит, остаётся связан с группой; учёт в лимите мест — открытый пункт (§14).
- **Ушёл** — членство закрыто; в текущий список тренировок не входит.

#### Игрок
Участник тренировок (профиль игрока). Может иметь абонементы и членства в группах.  
Внешний по отношению к узкому модулю сущность (общая карточка игрока клуба), но центральный субъект посещаемости и абонемента.

#### Тренер
Сотрудник, ведущий занятия. Назначается на группу и/или на конкретный слот / тренировку.  
В кабинете видит свои тренировки, отмечает посещаемость, может отменять занятие.

#### Админ / менеджер
Оператор клуба с полным доступом к планированию, составу, абонементам, посещаемости и сборам в рамках модуля.

---

### 2.3. Расписание и занятие

#### Слот расписания (расписание, schedule)
Повторяющийся недельный шаблон занятия группы: день недели, время начала/конца, площадка, тренер.  

Слот **не** является конкретной тренировкой. По слоту система **генерирует** экземпляры тренировок на горизонт (в v1 — 30 календарных дней вперёд).

#### Тренировка (занятие, экземпляр тренировки)
Конкретное занятие в дату и время: группа, площадка, тренер, статус.  

Может быть:
- создана из слота расписания (регулярная);
- создана вручную (разовая), без привязки к слоту.

Тренировка — единица, на которой отмечается **посещаемость** и к которой привязываются **доигровки**.

Статусы тренировки:
- **Новая** — ещё не закрыта / предстоит (или не финализирована).
- **Завершённая** — занятие проведено (обычно после работы с посещаемостью).
- **Отменённая** — занятие не состоится / отменено клубом; при уже отмеченном «был» — возврат списанного занятия на абонемент.

#### Генерация расписания
Автоматическое создание будущих тренировок по слотам на горизонт 30 дней.  
При изменении времени слота будущие тренировки со статусом «новая» по этому слоту удаляются и создаются заново; завершённые и отменённые не трогаются.

#### Список на тренировку
Кого тренер видит при проведении занятия в классическом контуре:
- активный **состав** группы;
- минус ушедшие **доигровкой** с этой тренировки;
- плюс пришедшие **доигровкой** / **дополнительным посещением** на эту тренировку.

Отдельной «записи на тренировку» с витрины в v1 нет.

---

### 2.4. Коммерция: продукт и абонемент

#### Шаблон продукта
Типовой пакет: сколько занятий входит в абонемент (и при необходимости базовые политики, например разрешение доигровок).  
Не привязан к цене конкретной группы; на его основе создаются **продукты** групп.

#### Продукт
Коммерческое предложение абонемента **для конкретной группы**: цена, цена продления, ссылка на шаблон (число занятий), признаки продажи.  

Покупка продукта → после confirm оплаты создаётся или продлевается **абонемент**.  
В v1 нет продуктов «свободного посещения» / MIX.

#### Абонемент
Именной пакет занятий игрока в рамках группы: остаток занятий (`N`), статус, даты создания/активации/закрытия, связь с продуктом.  

Абонемент — **учётный кредит занятий**, не платёжный документ. Деньги живут у платёжного шлюза / биллинга; модуль реагирует на confirm.

Статусы абонемента:
- **Неиспользован** — создан, занятия ещё не тратились (или не активирован по правилам продукта).
- **Активен** — используется, есть (или был) расход занятий.
- **Неактивен** — закрыт, обычно при нулевом остатке.

#### Остаток занятий (баланс абонемента)
Число тренировок, которые ещё можно «закрыть» отметкой «был».  
Уменьшается только при списании (§2.5), увеличивается при возврате (отмена «был», отмена тренировки после списания).

#### Продление абонемента
Покупка следующего пакета для того же игрока/группы (часто с ценой продления).  
В учёте — новый или продлённый абонемент по правилам продукта; состав группы как правило сохраняется активным.

#### Confirm оплаты (подтверждение шлюза)
Событие от платёжной системы о успешной оплате.  
Триггер создания/продления абонемента в модуле. Модуль сам оплату не проводит и карты не хранит.

### 2.5. Посещаемость и списание

#### Посещаемость
Факт учёта игрока на конкретной тренировке: **был** или **не был**, с привязкой к абонементу (если списание применимо) и опциональной статистикой (голы, передачи, лучший игрок).

Посещаемость создаётся/обновляется тренером или админом при проведении занятия (и при оформлении доигровок — по правилам сценария).

#### Отметка «был» (присутствовал)
Игрок посетил тренировку.  
**Единственное** основание для **списания** −1 с остатка абонемента в v1.

#### Отметка «не был» (отсутствовал)
Игрок из ожидаемых на занятии не явился.  
Остаток абонемента **не** меняется. Отдельных «заморозок» за пропуск в v1 нет.

#### Списание занятия
Уменьшение остатка абонемента на 1 в результате отметки «был».  
Должно быть идемпотентным: повторное сохранение той же отметки не списывает второй раз; снятие «был» возвращает 1.

#### Возврат занятия
Увеличение остатка абонемента на 1, если ранее было списание, а основание исчезло: сняли «был» или **отменили тренировку** после списания.

#### Отмена тренировки
Действие тренера/админа: занятие не проводится, статус → отменённая.  
Уже списанные за «был» занятия **возвращаются** на абонемент.  
Не путать с удалением тренировки.

#### Удаление тренировки
Физическое/жёсткое удаление записи о занятии. Разрешено **только** если нет посещаемостей.  
Используется для ошибочно созданных или пересоздаваемых «новых» экземпляров при смене слота.

---

### 2.6. Вместимость и дополнительные места

#### Лимит группы (вместимость)
Максимальное число игроков в составе группы (для активных — по правилу лимита).  
Базовая метрика «есть ли место принять в группу».

#### Дополнительное посещение (additional)
Разовый приход игрока на тренировку **не как регулярного члена ожидаемого слота**, в рамках разрешённых правил (часто связано с доигровкой или разрешёнными чужими группами).  
Учитывается в заполненности занятия и может иметь отдельный учётный след.

#### Дополнительные слоты тренировки
Лимит «гостевых»/доп. мест на конкретном занятии (`additional_capacity` / сколько уже занято).  
При создании тренировки ёмкость доп. слотов инициализируется из лимита группы.  
Используется, чтобы не переполнить занятие доигровками и доп. визитами сверх нормы.

#### Заполненность занятия
Расчёт «сколько человек фактически относится к этому занятию» для решения, можно ли ещё принять доигровку/доп.:  
активный состав − ушедшие доигровкой с этой тренировки + пришедшие доигровкой + additional.

---

### 2.7. Доигровки

#### Доигровка
Перенос обязательства с одной тренировки на другую: игрок не идёт на своё занятие A (или компенсирует пропуск), а идёт на занятие B.  
Это **боковой** сценарий классического контура, не отдельный продукт «свободного посещения» и не front-запись.

#### Доигровка current (перенос будущей)
Игрок заранее переносит **свою предстоящую** тренировку A на другую тренировку B.  
После оформления A для него «освобождается», B — цель визита. Отказ от только что оформленной доигровки — в коротком окне (в legacy ~30 минут).

#### Доигровка miss (за пропуск)
Игрок использует факт **прошлого пропуска**, чтобы посетить другую тренировку B.  
Число таких доигровок ограничено числом неперенесённых пропусков (и общими лимитами пакета).

#### Целевая тренировка / целевая группа
Тренировка (и её группа), **куда** оформлена доигровка.  
Целевая группа должна разрешать дополнительные посещения / доигровки; иначе оформить нельзя.

---

### 2.8. Сборы

#### Сборы (тренировочные сборы, camp)
Отдельный формат выездных / интенсивных мероприятий (не еженедельное занятие группы).  
Входит в scope рерайта, но детальные правила (запись, оплата, состав) описываются отдельным подразделом; не смешивать с сущностью **тренировка** еженедельного контура.

---

### 2.9. Термины вне scope v1 (чтобы не путать)

Ниже — слова из legacy/продукта, которые **не** являются частью v1. Если встречаются в старом коде — не переносить без нового продуктового решения.

| Термин | Кратко, почему вне scope |
|--------|---------------------------|
| **Front-запись** | RSVP игрока на конкретную тренировку с витрины (`TrainingRecord`). Другой контур. |

| **Заморозка** | Пропуск без списания занятия за счёт отдельного freeze-баланса. |
| **Пробная тренировка** | Разовый пробный визит / лид-воронка до покупки абонемента. |
| **Academia / source** | Второй продукт и мультитенантная метка в тех же таблицах. |

## 4. Доменная модель

```
Программа
  └── Группа (лимит мест, тренеры, площадки)
        ├── Расписание (день недели + время + площадка + тренер)
        │     └── экземпляры Тренировок
        ├── Состав (активен / пауза / ушёл)
        ├── Продукт / шаблон продукта
        └── Абонемент игрока

Тренировка (дата/время, статус, площадка, тренер)
  ├── Посещаемость (был / не был; опционально голы, передачи, лучший игрок)
  └── Доигровка (перенос с тренировки A на B)

Сборы — отдельный поддомен в том же рерайте (детализация позже)
```

Сущности **записи на тренировку** (`TrainingRecord`) в v1 **нет**.

### 4.1. Статусы тренировки

| Статус | Смысл |
|--------|--------|
| Новая | Предстоящая / ещё не закрыта |
| Завершённая | Занятие проведено (типично после работы с посещаемостью) |
| Отменённая | Занятие отменено |

### 4.2. Модель группы

Группа в v1 — всегда **фиксированная** (аналог legacy `only-abonement`):

- лимит = вместимость состава;
- из расписания генерируются экземпляры тренировок;
- режим `frontend` и флаги front-записи **не используются**.

---

## 5. Генерация расписания

1. При создании слота расписания (и при смене времени слота) система создаёт экземпляры тренировок на **следующие 30 календарных дней**, совпадающие с днём недели слота.
2. При смене времени слота:
   - удаляются будущие тренировки со статусом **новая** по этому schedule;
   - заново создаются на горизонт 30 дней;
   - тренировки со статусами **завершённая** и **отменённая** не трогаются.
3. Разовая тренировка может быть создана вручную.

---

## 6. Абонемент и состав

1. По confirm оплаты создаётся абонемент (или продлевается) с балансом `N` занятий согласно продукту **группы**.
2. Игрок связывается с группой через **состав** (`активен` / `пауза` / `ушёл`).
3. Статусы абонемента: неиспользован → активен → неактивен при нулевом остатке занятий.
4. Заморозки **отсутствуют**.
5. Продукты свободного посещения / MIX в v1 **не поддерживаются**.

---

## 7. Списание занятий

1. Списание **−1** занятия — **только** когда тренер отметил игрока как **«был»**.
2. Отметка **«не был»** — баланс абонемента **не** меняется.
3. Повторная смена отметки корректно пересчитывает баланс (снятие «был» → возврат; повторная установка «был» → списание), без двойного списания.
4. Списания в момент записи на занятие **нет** (самого механизма записи в v1 нет).

---

## 8. Отмена и удаление тренировки

1. **Отмена тренировки** (тренер / админ):
   - статус → отменённая;
   - если у игрока уже была отметка **«был»** и занятие списано — **вернуть +1** на абонемент.
2. **Удаление** тренировки разрешено только если нет записей посещаемости.

## 9. Вместимость

В классическом контуре базовый лимит — **состав группы**.

### 9.1. Места в группе

```
свободные места в группе = лимит группы − число активных игроков в составе
```

(Уточнение по paused: как учитывать в лимите — сверить с исходником при реализации состава.)

### 9.2. Фактическая заполненность занятия (для доигровок / доп.)

Как в исходнике для `getPlayersCount`:

```
активный состав
− игроки, ушедшие доигровкой с этой тренировки
+ доигровки «на эту» тренировку
+ additional-посещения
```

Свободно для доигровки/доп.: `лимит группы − getPlayersCount`.

### 9.3. Дополнительные слоты тренировки

При создании тренировки `additional_count` копируется с `limit` группы.  
Свободные доп. места: `additional_count − additional_current`.

Формулы front-записи (`TrainingRecord` + состав) в v1 **не применяются**.

## 10. Доигровки

В v1 **оставляем** как боковой сценарий классического контура (не как замену front-записи).

### 10.1. Типы

| Тип | Смысл |
|-----|--------|
| `current` | Перенос своей **будущей** тренировки на другую |
| `miss` | Визит на другую тренировку **вместо прошлого пропуска** |

### 10.2. Ограничения (ориентир по исходнику; детальная матрица — при проработке)

- Лимит доигровок относительно размера пакета (в исходнике: не больше половины занятий пакета для ряда сценариев).
- Для `miss` — не больше числа неперенесённых пропусков.
- Целевая группа должна разрешать additional / доигровку.
- Отказ от оформленной доигровки `current` — в ограниченном окне (в исходнике ~30 минут).
- Отдельные продукты могут запрещать доигровки.

Точная матрица «куда можно перенести» выносится в подпункт при детализации и сверяется с текущим `RescheduleForm` / хелперами.

## 11. Основные сценарии

### 11.1. Планирование

1. Создать/изменить группу и слоты расписания.
2. Система генерирует экземпляры тренировок (см. §5).
3. При необходимости создать разовую тренировку вручную.

### 11.2. Состав и абонемент

1. Оплата → confirm шлюза → абонемент создан/продлён.
2. Игрок в составе группы (активен).
3. Списание только по отметке «был».
4. При остатке 0 абонемент неактивен; email о низком остатке/окончании — в списке событий (§12).

### 11.3. Проведение занятия

1. Тренер/админ открывает тренировку: **состав группы** + доигровки/доп. на это занятие.
2. Отмечает **был / не был** (опционально голы, передачи, лучший игрок).
3. При **«был»** — списание с абонемента (§7).
4. При необходимости отменяет тренировку (§8).

### 11.4. Доигровки

См. §10.

### 11.5. Сборы

Входят в рерайт. Детальное ТЗ — отдельный подраздел после стабилизации ядра weekly-тренировок.
